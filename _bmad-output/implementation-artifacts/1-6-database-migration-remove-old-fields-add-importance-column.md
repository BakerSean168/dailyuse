**Observations:**

**Critical finding:**

- Decision: Keep as Int OR convert to string enum (recommend keeping Int for now)

   - Note: taskInstance doesn't have importance/urgency directly

**Current field definitions:**

### Migration Strategy

**Recommended approach (Prisma-managed):**
1. Update schema.prisma
2. Run `prisma migrate dev`
3. Prisma detects schema drift and generates SQL

**SQL operations expected:**
```sql

-- Importance already exists, no need to add
-- But verify constraints if changing type

-- Update any NULL importance values to default

```

### IntEnum vs String Enum Decision

**Current implementation:** `importance Int // (0-4)`

**Options for this migration:**
1. **Keep Int (Recommended for MVP)** - No type change, just remove urgency
2. **Convert to String Enum** - More readable but requires data transformation

**For this story:** Keep Int to minimize breaking changes
- Application layer already handles conversion (calculatePriority)
- DTOs use ImportanceLevel enum
- Database can stay with Int for performance

### Data Migration Logic

**Current importance Int values:**
- 0 = Trivial
- 1 = Minor
- 2 = Moderate (default)
- 3 = Important
- 4 = Vital

**Default handling:**
- New tasks created after migration will have importance = 2 (Moderate)
- Existing tasks: keep current importance values
- No data loss expected
