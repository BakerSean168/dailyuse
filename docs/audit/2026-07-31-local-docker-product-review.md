# 2026-07-31 本机 Docker 产品复审

## 结论

MemoFlow 已能让用户在不配置 AI 的情况下分别创建目标、快速任务、提醒和日程，
并能在日历中看到、完成今日任务。提醒与独立日程的基础流程可用，日历对任务的
自动汇入也符合预期。

但产品目前还不能稳定完成“目标 → 关键结果 → 完整任务计划 → 完成后贡献进度”
这一核心闭环。目标与关键结果存在多处刷新和草稿提交问题；在本轮手工路径中，
为“先创建目标、后补关键结果”的目标选择任务关联时，业务面板直接崩溃并丢失
任务表单草稿。因此当前基础功能是**分别可用、联动不可靠**，尚不适合宣称完整
业务闭环已经优雅可用。

AI 工作区的结构方向正确：左侧会话、中央 AI、右侧业务面板、业务标签和可恢复
上下文已经存在。但在 1280×720 桌面视口下，它还没有达到 ChatGPT/Codex 桌面端
的克制程度与层级清晰度，尤其是顶部模块胶囊、右侧标签栏、中央宽度和输入区比例。

## 分级发现

### P0：后补 KR 的目标在任务绑定时可令业务面板崩溃

复现路径：

1. 创建目标，不在创建弹窗中正式添加 KR。
2. 进入目标详情，新增一个 KR。
3. 进入任务，创建完整任务计划并启用“关键结果关联”。
4. 在“选择目标”中选择该目标。

结果：整个右侧业务面板进入错误边界，显示
`Cannot read properties of null (reading 'focus')`。点击“重试”可以恢复任务列表，
但任务标题、描述和关联设置全部丢失。

已有 `core-product-phase-a` P0 用例通过，说明这不是所有目标都必现；测试只创建了
“目标创建时同时添加 KR”的数据。需要新增“创建后补 KR”回归路径，并在 Select
重新渲染后恢复焦点时防御空 trigger/ref。

### P1：目标创建弹窗会静默丢弃 KR 草稿

用户在“关键结果”标签页填写标题和目标值后，如果没有再点击内容区中的
“添加关键结果”，直接点击底部“创建目标”，目标仍会成功创建，但 KR 为 `0/0`。
表单没有阻止提交、没有提示未添加草稿，也没有自动提交当前草稿。

建议只保留一种提交模型：当前 KR 表单有效时由“创建目标”一起提交，或在离开标签/
提交目标时明确确认丢弃；不要同时出现内容区和底部两个语义接近的提交动作。

### P1：KR 新增、记录与目标摘要刷新不一致

- 新增 KR 后，详情中已经出现 KR 卡片，但目标摘要仍显示 `0/0`，刷新后才变成 `0/1`。
- 紧接着录入进度时，弹窗关闭但没有新增记录，控制台只记录“未找到关键结果”，
  页面没有错误反馈。
- 刷新后使用快捷值 `1` 再保存可以成功，KR 显示 `1 / 10`，但目标摘要仍显示 `0%`。

这是同一类缓存/查询失效问题。创建 KR、创建记录后应统一失效目标详情、KR 列表、
目标统计和今日概览；写操作失败必须保留弹窗与输入，并显示可恢复错误。

### P1：本地 Docker 的机器端口覆盖没有同步 CORS（本轮已修复）

原部署将 Web 映射到 `12137`，但 API CORS 仍只允许共享默认端口 `58080`，导致页面
可以打开、所有容器也均为 healthy，但注册等 API 请求统一返回 403。

本轮已让 `createLocalComposeRuntimeEnv()` 根据最终 `WEB_HOST_PORT` 合并
`LOCAL_DOCKER_CORS_ORIGIN` 和 AI `ALLOWED_ORIGINS`。修复后注册、验证码、登录和
业务写入均成功。

### P1：AI 服务商“默认”开关表达了不可能状态

AI 设置页中 Gemini、OpenRouter、OpenAI 都显示“尚未接入”，但三个“设为默认”
开关在可访问性树中同时为 checked。默认服务商应是单选关系，而且未接入的服务商
不应显示为当前默认。建议改为单选或“接入并设为默认”的显式选项。

### P1：AI + 业务并列时，中央工作区被压缩且操作行拥挤

1280px 视口下：左侧会话栏 260px，AI 列 570px，业务面板 450px。AI 输入区随列宽
缩到 570px，但底部仍同时放置意图、执行引擎、211px 的模型提示和 98px 发送按钮，
信息密度明显高于 ChatGPT/Codex。日程周视图在 449px 内容宽度中也只能截断事件名。

建议引入明确的宽度策略：AI 主列设可用最小宽度，业务面板在窄桌面默认预览/抽屉，
进入“专注业务”时再占更大空间；输入区次要控件折叠到一个工具菜单。

### P2：业务标签栏没有达到 Codex 桌面端的层级和可读性

Codex 参考中，任务/Review 等标签属于稳定的顶层工作区标签，标签拥有清晰文本、
关闭区和新增入口。MemoFlow 的业务标签被限制在 450px 右面板顶部；四个标签已经
压缩到约 90px，每个关闭按钮仅 16px 高，且与顶部 26–30px 的图标胶囊形成两套
并行导航。

建议将“AI 会话”和“业务工作面板”统一成一层桌面工作区标签模型：标签文本、选中态、
关闭、新建/更多保持同一高度与间距；顶部模块图标降级为启动器，而不是第二套标签栏。

### P2：AI 空状态与输入区存在重复动作和宽度不一致

隐藏业务面板时，欢迎内容约 672px 宽，输入区却约 896px 宽；显示面板后两者一起
缩到约 522–570px。空状态同时出现“配置 AI”和“去配置模型”，输入框又保持禁用，
形成三个重复信号。

建议使消息内容和 composer 使用同一 max-width；保留一个主 CTA，将禁用输入区改为
可点击的解释状态或在输入区内直接提供唯一配置入口。

### P2：若干交互控件缺少键盘/读屏语义

- 进度快捷值 `1/2/5/10` 是带 `cursor-pointer` 的 `div`，没有 role、tabindex 或按钮语义。
- 已完成任务详情的关闭按钮没有可访问名称。
- AI 设置中的服务商默认开关没有独立可访问名称。

这些控件应使用原生 button/radio/switch，补齐名称、焦点态和键盘操作。

## 优先实施顺序

1. 修复“后补 KR → 任务选择目标”崩溃，并新增对应 P0 E2E。
2. 统一 KR 创建/记录后的查询失效与错误恢复，保证页面无需刷新。
3. 消除目标创建中的 KR 草稿双提交模型。
4. 修正 AI 默认服务商状态模型。
5. 统一桌面标签系统和 1280px 下 AI/业务面板宽度策略。
6. 收敛 AI 空状态 CTA、composer 控件和可访问性语义。
